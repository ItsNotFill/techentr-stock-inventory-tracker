# DECISIONS.md

A short log of design decisions, so later sessions do not undo earlier choices. Add new entries at the bottom with the date. Change a decision only by adding a new entry that replaces it.

## Core design (from SPEC.md)

| # | Decision | Reasoning |
| --- | --- | --- |
| 1 | **Ledger table.** Every stock change is one row in `stock_movements`; stock is `SUM(qty_delta)`; there is no `current_stock` column. | Any stock figure can be traced to the movements behind it, and there is no second number that can drift out of sync. |
| 2 | **Base units.** Quantities are stored in g, ml or unit as `numeric`, never floats; packs are converted on screen only. | One unit per ingredient removes conversion bugs, and exact decimals keep the euro figures exact. |
| 3 | **Idempotent imports.** `UNIQUE(location_id, pos_order_id)` on `sales`; orders already imported are skipped. | Uploading the same file twice must never deduct stock twice. |
| 4 | **AI photo reading with a confirmation screen.** A vision model reads POS screenshots, end-of-day reports and supplier invoices; every result is a draft until a user confirms it, and the photo is stored with it. | The model can misread, so a person checks before anything touches stock, and a wrong reading can be traced back to its photo and undone. |
| 5 | **"Unexplained usage" framing.** Variance is called "unexplained usage" in the UI and tied to portioning, costing and waste. | Owners buy a cost tool; staff will not use something that feels like surveillance. |

## Decided in the planning session (2026-11-16)

| # | Decision | Reasoning |
| --- | --- | --- |
| 6 | **AI and offline tasks are folded into stages 2 to 5**, after each stage's manual path and done check. | The maths is proven by hand before AI is added on top, and the plan stays at eight stages. |
| 7 | **AI provider is the Claude API**, called only from `lib/ai` on the server, with the model set by `AI_MODEL` (default: see entry 30). | One provider keeps the module small; an env var lets us switch to a cheaper model without a code change. |
| 8 | **A count changes the ledger only after a manager or owner approves it.** Statuses: draft, submitted, approved, rejected. A manager or owner who counts can submit and approve in one step. | A typo in a count would otherwise rewrite stock and the euro report immediately. |
| 9 | **Count time is the moment staff submit.** On approval, theoretical stock is computed as of that moment. | Sales and deliveries recorded between submit and approval must not be swallowed by the count. |
| 10 | **Late movements are auto-corrected.** A movement dated before an approved count but recorded after it also writes an offsetting `count_adjust` on that count, and the count's unexplained usage is recomputed. | The count already absorbed those sales, so deducting them again would double-count; this keeps stock right whatever order things are entered in. |
| 11 | **Movements carry two timestamps:** `occurred_at` (when it happened) and `created_at` (when it was recorded). | Decisions 9 and 10 need to know what stock was at a past moment, which insertion time alone cannot tell. |
| 12 | **Import undo deletes the import's sales and their movements** inside one database function, the only path allowed to delete from `stock_movements`. The `sales_imports` row stays with status `undone`. | SPEC.md asks for deletion so the file can be re-imported cleanly; keeping the import row preserves the audit trail and the photo. |
| 13 | **Opening counts are flagged** (`count_lines.is_opening`) and left out of unexplained-usage totals. | The first count of an ingredient has no theoretical stock, so its "variance" is just the opening balance. |
| 14 | **`location_id` is on every table**, including child tables. | One RLS policy shape covers everything, with no joins inside policies. |
| 15 | **Three tables beyond the spec's fourteen:** `deliveries`, `delivery_lines`, `ai_extractions`. | Invoice photos need a draft that can be reviewed before stock is added; every AI read needs its photo, raw output and status kept. |
| 16 | **Draft AI recipe lines may name an ingredient that does not exist yet** (`draft_ingredient_name`); the ingredient is created or matched when the recipe is confirmed. | SPEC.md creates ingredients from confirmed recipes, so a draft cannot require them up front. |
| 17 | **Only confirmed recipe lines deplete stock.** `menu_items.is_mapped` is true only when the item has a confirmed recipe. | An unreviewed AI guess must never move stock. |
| 18 | **Recipe changes apply to future sales only.** Movements already written are not recalculated. | The ledger is append-only; rewriting history would make past reports change under the owner's feet. |
| 19 | **Photo sales use one synthetic order per report**, `pos_order_id = eod:<business date>`, and the app warns if CSV sales already exist for that date. | An end-of-day report has no order IDs; this keeps the idempotency rule and catches the same day entered twice. |
| 20 | **Invoice-photo deliveries are confirmed by a manager or owner**; staff can upload the photo and log manual deliveries. | Confirming an invoice updates ingredient costs, which drives every euro figure. |
| 21 | **Cost snapshots** are stored on `count_lines.unit_cost` and `delivery_lines.unit_cost`. | Past euro figures must not move when an ingredient's cost changes later. |
| 22 | **POS items that use no stock can be ignored** (`menu_items.is_ignored`). | Service charges and gift cards would otherwise sit in the unmapped queue for ever. |
| 23 | **RLS is enforced through Drizzle:** app queries run as the signed-in user through `lib/db/client.ts`; `lib/db/admin.ts` bypasses RLS and is used only for migrations, seed and sign-up bootstrap. | A plain Drizzle connection uses a privileged role that silently skips RLS, which would break tenant isolation. |
| 24 | **All members of a location can read its rows; writes depend on role.** Hiding costs and theoretical stock from staff is done in the screens. | Postgres RLS works on rows, not columns; column-level rules are not worth the complexity for the MVP. |
| 25 | **Tooling:** npm, Vitest, `decimal.js` for quantity maths, Serwist and IndexedDB for the PWA and offline counts. | Common, well-documented choices; `decimal.js` because Postgres `numeric` arrives in JS as a string and JS numbers are floats. |
| 26 | **Refunds are sale lines with a negative quantity**, which write positive movements. | A refunded item was not used, and corrections must be new movements, not edits. |
| 27 | **Supabase project setup:** automatic RLS is on for new tables, and new tables are not exposed to the Data API. All table access goes through Drizzle on the server; `supabase-js` is used only for Auth and Storage. | With the Data API closed, the browser's anon key cannot reach any table, so a missing or wrong policy cannot leak data; RLS stays on as the second layer behind the server. |
| 28 | **Tenant integrity is enforced by keys.** Every parent table has `UNIQUE(id, location_id)` and every child uses a composite foreign key `(parent_id, location_id)`. Extends entry 14. | RLS checks only the row being written, so without this a row in one location could reference another location's ingredient or menu item; now the database refuses it. |
| 29 | **One agent works sequentially by default.** Sub-agents are only for independent UI tasks, at most two at a time, and two tasks that touch the schema or migrations never run at the same time. | Most tasks build on the one before; parallel schema changes produce conflicting migrations, and every sub-agent starts cold and costs extra usage. |
| 30 | **`AI_MODEL` defaults to `claude-sonnet-5-5`.** Replaces the default in entry 7. | Reading a photo into JSON is routine extraction, so the cheaper, faster model is the right starting point; the env var can raise it if readings turn out poor. |

## Decided before stage 0 (2026-11-16)

| # | Decision | Reasoning |
| --- | --- | --- |
| 31 | **Supabase keys are the new publishable and secret keys:** `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_SECRET_KEY`. Replaces the `anon` and `service_role` names used in earlier entries and docs. | These are the keys the Supabase project issues; the old names would point at keys that are not in `.env.local`. |
| 32 | **Two database URLs.** `DATABASE_URL` is the transaction pooler (port 6543) and is used by the app, with the Drizzle client created with `prepare: false`. `DATABASE_URL_MIGRATIONS` is the session pooler (port 5432) and is used by `drizzle-kit` migrations and the seed script. | Serverless functions need the transaction pooler, which does not support prepared statements; migrations and seeding need a session. |
| 33 | **Operating mode: the main agent orchestrates.** It does the schema, migrations, ledger, depletion, variance, import logic and `lib/ai` itself. Screens, forms, styling and small fixes go to the `ui-builder` sub-agent. The `reviewer` sub-agent checks every stage before the merge. Work is sequential; never two schema or migration tasks at once. Extends entry 29. | The parts that must never be wrong stay with the strongest model; screens are cheaper to delegate; a second pair of eyes checks each stage. |
| 34 | **The main agent does not stop for questions it can answer reasonably.** It picks the option most consistent with `SPEC.md` and `DECISIONS.md`, records it here, and continues. It stops only for: a secret or key missing from `.env.local`; an action that needs Filippo's accounts (Vercel, Supabase dashboard, Anthropic console); anything destructive to the database or the `main` branch. Replaces the "stop and ask" rule. | The build runs unattended; a wrong small choice is cheap to change later because it is written down, while a stalled session costs a whole usage window. |
| 35 | **Checkpoints.** `PROGRESS.md` has a "Now working on" line naming the task, branch and worktree. Long tasks get pushed WIP commits. Every session starts by checking `git status`, `git worktree list` and that line, and finishes or cleans up half-done work first. | A usage limit can end a session at any moment; the next session must be able to continue from the repository alone. |
| 36 | **`NEXT_STEPS_FOR_FILIPPO.md` is the hand-off file.** It lists what only Filippo can do (Vercel clicks, keys) and gets a five-line summary after each stage. | One place to look after an unattended run. |

## Decided in stage 0 (2026-11-16)

| # | Decision | Reasoning |
| --- | --- | --- |
| 37 | **Drizzle RLS names checked against the installed version** (`drizzle-orm` 0.45, `drizzle-kit` 0.31). The names in `SCHEMA.md` are right: `pgPolicy(name, { as, for, to, using, withCheck })` in the table's third argument, `.enableRLS()` on a table with no policies, and `authenticatedRole`, `anonRole`, `authUsers`, `authUid` from `drizzle-orm/supabase`. One addition: `drizzle.config.ts` sets `entities: { roles: { provider: "supabase" } }`. | Without the `entities` setting drizzle-kit tries to create or drop Supabase's own roles. | 39 | **shadcn/ui uses the Radix base with the Nova preset.** Forms use the `field` components; the old `form` component no longer exists in the registry. | Radix is the long-standing base with the most examples; `field` is what shadcn now ships for forms. |
| 40 | **Postgres is version 17**, so `ON DELETE SET NULL (pack_size_id)` in `delivery_lines` can be used as planned in `SCHEMA.md`. | The column-list form needs Postgres 15 or later. |
| 41 | **The stage 0 test table is `setup_check`**, with RLS on and no policies. `scripts/check-db.ts` checks both database URLs and that the table exists. | Proves migrations reach the database without exposing anything: with no policies only the admin connection can read it. |
| 42 | **Stage 0 is merged and stage 1 starts before the Vercel deploy exists.** The Vercel task stays unticked in `PROGRESS.md` until Filippo has created the project. | Vercel deploys `main`, so the app has to be on `main` before the project can be created, and creating it needs Filippo's account. Filippo asked for work to continue meanwhile. The other half of the done check, the test table, passes. |

## Decided in stage 1 (2026-11-16)

| # | Decision | Reasoning |
| --- | --- | --- |
| 43 | **The app runs its queries as a dedicated database role, `app_user`**, not Supabase's `authenticated`. `lib/db/client.ts` switches to it inside each transaction and sets the user's id in `request.jwt.claims`. Every RLS policy is written `to app_user`, and every table migration ends with hand-written `GRANT`s to `app_user`. Policies read the user through `public.current_user_id()`, because `app_user` cannot use `auth.uid()`. Refines entries 23 and 27; where `SCHEMA.md` says "revoked from `authenticated` and `anon`", read "never granted to `app_user`, `authenticated` or `anon`". | In this Supabase project, tables made by migrations give `authenticated` no rights. Granting them would open every table to the Data API for any signed-in user, which entry 27 rules out. The Data API can only act as `anon`, `authenticated` or `service_role`, so rights given to `app_user` stay reachable from our server only. |
| 44 | **Two helper functions beyond the plan:** `list_location_members(loc)` returns the team with e-mail addresses to owners and managers; `find_user_id_by_email(loc, email)` lets an owner add someone who already has an account. Both are `SECURITY DEFINER` with an empty search path. | E-mail addresses live in `auth.users`, which the app role cannot read, and the admin connection is reserved for migrations, seed and sign-up bootstrap. |
| 45 | **Sign-up is for owners; everyone else is invited.** Sign-up uses e-mail and password. After the first login a user with no restaurant lands on `/onboarding`, which creates the organization, the first location (same name) and the owner membership. E-mail links land on `/auth/confirm`, which accepts both Supabase link styles. | SPEC.md: "owner creates the organization and first location". Invited users already have a membership, so they skip onboarding. |
| 46 | **The dashboard is open to every role; euro figures are for owners and managers only.** Staff see the dashboard without money. The Ingredients screen is in the menu for owners and managers, Settings for owners. Role rules live in `lib/auth/roles.ts`. | SPEC.md gives the dashboard to owner and manager, but staff need a landing screen before the count screen exists; entry 24 already says costs are hidden from staff in the screens. |
| 47 | **The MVP shows one location per user:** the first one they joined. | SPEC.md keeps multiple locations out of the MVP UI; the data model already supports them. |
| 48 | **Every Supabase client waits for a real request (`await connection()`) before it is built.** | With Cache Components, Next.js rejects reading the clock during a prerender, and the Supabase client does that when it is created. |
| 49 | **Team invites are one-time links, not e-mails.** Inviting someone creates their account and shows the owner a link to pass on (by chat or e-mail). The link signs the person in once and takes them to "choose a password". An owner can make a fresh link for anyone on the team, which also covers a forgotten password. Someone who already has an account is added to the team directly. Refines "Supabase Auth invites" in `SCHEMA.md`. | Supabase's built-in e-mail sender only delivers to the project team's own addresses and a few messages per hour, so e-mailed invites would fail for real staff until SMTP is set up. A link works today and needs no configuration. |
| 50 | **Ingredient forms use readable units.** Cost is typed per kg, per l or per unit, and reorder point and par level in g/kg or ml/cl/l; the server converts to base units with `lib/units`. An ingredient's unit is fixed while it has pack sizes (and, from stage 3, movements). Archived ingredients keep their name reserved. | Nobody thinks of mozzarella as EUR 0.008 per gram; storage stays in base units as decision 2 requires. |

## Decided in stage 2 (2026-11-16)

| # | Decision | Reasoning |
| --- | --- | --- |
| 51 | **A menu item is mapped, ignored or unmapped, never mapped and ignored at once** (database check). An item with a recipe cannot be ignored until its lines are removed; giving an ignored item a recipe makes it mapped. | Entry 22 says ignored items use no stock; allowing both flags would leave it unclear whether a sale depletes. |
| 52 | **A recipe is saved as a whole.** The lines in the editor replace the stored ones, every saved line is confirmed, and `is_mapped` follows from whether any line is left. Amounts are typed in a readable unit and stored in the ingredient's base unit. Archived ingredients cannot be put in a recipe. | One save keeps `is_mapped` and the lines in step inside one transaction; entry 17 needs that flag to be exact. |
| 53 | **Uniqueness of menu items:** the POS id when the item has one, otherwise the POS name without regard to case. Two items may share a name if the POS gives them different ids. | This is how sales rows will be matched in stage 3 (`SCHEMA.md`, `menu_items`). |
| 54 | **`menu_items.ai_extraction_id` has no foreign key yet.** It is added in the migration that creates `ai_extractions`. | The AI tasks come after the stage's done check, and the table does not exist before them. |
| 55 | **End-to-end tests run in a headless browser (Playwright, `npm run test:e2e`).** One spec per pair of stages clicks through the real screens against the real database and removes what it creates. | Nobody watches the screens during an unattended build. The first run found two bugs that unit and HTTP tests could not: typed values wiped after a failed submit, and field ids clashing with hidden copies of earlier screens. |
| 56 | **Forms keep their fields in state and build field ids with `useId()`; "new item" forms empty themselves after a create.** | React resets uncontrolled fields after every Server Action, and Next.js 16 keeps earlier screens mounted but hidden, so fixed ids collide. See "Framework notes" in `CLAUDE.md`. |
| 57 | **The AI tasks are parked until `ANTHROPIC_API_KEY` exists; the stages do not wait for them.** A stage is merged when its manual path and done check pass and the reviewer says OK. Each stage's AI block ("AI onboarding", "Sales by photo", "Restock by invoice photo") stays unticked in `PROGRESS.md` and is built later on its own branch (`stage-2-ai-onboarding`, and so on). The `ai_extractions` table, the `photos` bucket and `lib/ai` come with the first of them. | Filippo asked for the non-AI work to continue while the key is missing. Entry 6 already orders each stage as manual path, done check, then AI, so nothing in the manual path depends on the AI block. |
